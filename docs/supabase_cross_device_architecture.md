# Supabase Cross-Device Architecture Plan

This document prepares `مصروف السكن الجماعي / Shared Housing Expenses` for real Android/iOS cross-device network sharing while preserving the current local-first app behavior until migration is safe.

## Current Architecture Review

The app currently uses `ExpenseNetworkRepository` as the main boundary between UI and persistence. `SharedPreferencesExpenseNetworkRepository` stores all networks as one JSON list under `expense_networks_v1`, notifications under `expense_network_notifications_v1`, and active session values under `active_network_name` / `active_member_id`.

Current local entities are nested:

- `ExpenseNetwork`
  - `id`
  - `name`
  - `password`
  - `currencyCode`
  - `currencySymbol`
  - `members`
- `Member`
  - `id`
  - `name`
  - `passwordHash`
  - `passwordSalt`
  - `createdAt`
  - `expenses`
- `Expense`
  - `id`
  - `amountCents`
  - `note`
  - `createdAt`
  - `addedByMemberId`
  - `addedByMemberName`
- `NetworkNotification`
  - `id`
  - `networkId`
  - `recipientMemberId`
  - `actorMemberName`
  - `expenseAmountCents`
  - `currencySymbol`
  - `noteSnippet`
  - `createdAt`
  - `isRead`

The current repository abstraction is a good start, but cloud migration should split responsibilities more clearly:

- Network/member/expense operations: cloud-backed.
- Session cache: local `shared_preferences`.
- Language preference: local `shared_preferences`.
- Optional offline cache: local, separate from source-of-truth repository.

## Entities That Must Become Cloud-Backed

Cloud-backed:

- Networks
- Network members
- Expenses
- Network notifications

Local-only or mostly local:

- Selected language: keep in `shared_preferences`.
- Active session cache: keep in `shared_preferences`, storing cloud `network_id` and `member_id`.
- Optional offline cache: may use `shared_preferences`, SQLite, or Drift later, but should not be the source of truth once Supabase is enabled.

## Proposed Supabase Schema

Use UUID primary keys generated by Supabase. Store money in cents as integers. Store timestamps as `timestamptz`.

### `networks`

```sql
create table public.networks (
  id uuid primary key default gen_random_uuid(),
  name text not null,
  normalized_name text not null unique,
  network_password_hash text not null,
  network_password_salt text not null,
  currency_code text not null default 'USD',
  currency_symbol text not null default '$',
  created_by_member_id uuid,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Notes:

- `normalized_name` supports join-by-name behavior across devices.
- The current local `password` must become `network_password_hash`.
- `created_by_member_id` can be filled after creator member insert, or omitted if circular creation is inconvenient.

### `network_members`

```sql
create table public.network_members (
  id uuid primary key default gen_random_uuid(),
  network_id uuid not null references public.networks(id) on delete cascade,
  name text not null,
  normalized_name text not null,
  password_hash text not null,
  password_salt text not null,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  unique (network_id, normalized_name)
);
```

Notes:

- This preserves member-level account passwords.
- Duplicate member names are prevented per network.
- If Supabase Auth is adopted later, this table can be linked to `auth.users`, but the current app can start without full user accounts.

### `expenses`

```sql
create table public.expenses (
  id uuid primary key default gen_random_uuid(),
  network_id uuid not null references public.networks(id) on delete cascade,
  paid_by_member_id uuid not null references public.network_members(id),
  added_by_member_id uuid not null references public.network_members(id),
  added_by_member_name text not null,
  amount_cents integer not null check (amount_cents > 0),
  note text check (char_length(note) <= 200),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Notes:

- Current UI adds expenses for the active member. If payer selection is added later, `paid_by_member_id` and `added_by_member_id` can differ.
- `added_by_member_name` is denormalized for notification/history display resilience.

### `network_notifications`

```sql
create table public.network_notifications (
  id uuid primary key default gen_random_uuid(),
  network_id uuid not null references public.networks(id) on delete cascade,
  recipient_member_id uuid not null references public.network_members(id) on delete cascade,
  actor_member_id uuid references public.network_members(id) on delete set null,
  actor_member_name text not null,
  expense_id uuid references public.expenses(id) on delete cascade,
  expense_amount_cents integer not null,
  currency_symbol text not null,
  note_snippet text,
  is_read boolean not null default false,
  created_at timestamptz not null default now()
);
```

Notes:

- For Phase 4, insert notifications for all other members after an expense insert.
- Supabase Realtime can later subscribe to notifications by `recipient_member_id`.

## How Android and iPhone Users Join the Same Network

1. Creator on Android or iPhone creates a network.
2. App inserts `networks` row with normalized network name, hashed network password, and currency metadata.
3. App inserts creator into `network_members` with member password hash.
4. Another user opens the app on Android or iPhone.
5. User enters network name and network password.
6. App queries by `normalized_name`, verifies the network password hash, then creates a `network_members` row with the new member name and member password hash.
7. Both users now read/write the same `network_id`.
8. Expenses and notifications are synced by `network_id`.

## Security Risks

- Current hashing helper is lightweight and local-only. For production, use stronger password hashing strategy. Flutter apps cannot safely keep server secrets.
- Supabase anon key is public by design. RLS policies must protect all data.
- If not using Supabase Auth, RLS is harder because member-password login is app-level, not database-auth-level.
- Network passwords and member passwords must never be stored as plaintext.
- Do not allow arbitrary reads from `networks`, `network_members`, `expenses`, or notifications without membership checks.

Recommended production direction:

- Use Supabase Auth anonymous or email/phone auth per device/user.
- Link `network_members.user_id` to `auth.users.id`.
- Use RLS policies based on authenticated user membership.

## Migration Risks

- Existing local IDs are custom strings; Supabase should use UUIDs. Migration requires ID mapping.
- Existing networks may have plaintext network password locally.
- Old members may not have personal passwords.
- Offline writes can conflict with cloud writes.
- Notifications may duplicate if local and cloud generation both run.

Safe migration approach:

1. Keep local mode.
2. Add export/migration mapper.
3. Let user opt in to upload one network.
4. Create cloud network and members.
5. Map local IDs to cloud UUIDs.
6. Upload expenses.
7. Generate or skip historical notifications.
8. Switch active session to cloud network only after successful upload.
