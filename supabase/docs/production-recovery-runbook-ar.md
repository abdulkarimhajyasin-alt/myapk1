# دليل تشغيل الاستعادة والموافقات — Maskan

الحالة: إجراءات محلية متاحة الآن؛ إجراءات الإنتاج أدناه **خطة غير منفذة تتطلب موافقة مستقلة**. لا يغير هذا الدليل صلاحيات المهمة الحالية. القرار المرجعي في [تقرير التدقيق](production-recovery-audit-ar.md).

## أ. إعادة البروفة الاصطناعية

المتطلبات: نفس checkout المعتمد وDocker المحلي وPython 3.11+ وNode وFlutter واعتمادات المشروع. لا تُدخل أي URL إنتاجي أو نسخة حقيقية في `.codex_tmp`. أبقِ البيئة السابقة `maskan-hardening-local` دون تغيير.

```powershell
python supabase/staging/staging.py start
python supabase/staging/staging.py inspect
python -m unittest discover -s supabase/audit -p test_audit_safety.py -v
python supabase/staging/isolation_check.py
python supabase/staging/backup_restore.py
python supabase/staging/recovery_validation.py
python supabase/audit/compare_schema.py
```

شغّلها بالتتابع. backup_restore يوقف كتّاب API المحليين مؤقتًا ويأخذ dump ثنائيًا للبيانات الاصطناعية، ثم يستعيده إلى `maskan-staging-recovery` فقط. إعادة هذا الأمر تستبدل قاعدة recovery الاصطناعية؛ لا تمس الإنتاج أو بيئة الاختبار القديمة. تحقق من نجاح parity قبل اختبار العملاء. لا تستعمل redirection نصيًا في PowerShell لملف dump ثنائي.

recovery_validation يلغي معاملة اصطناعية ثم يشغّل PostgREST على `127.0.0.1:57321` بشبكة recovery، ويختبر المكتبتين ويوقف الحاوية في النهاية. database recovery يبقى على `127.0.0.1:57322`. ملفات env وJWT والنسخة والسجلات تحت `.codex_tmp` فقط. الفحص لا يشغّل Auth أو Edge أو Realtime كاملًا على recovery. إذا انقطع المضيف أثناء الاختبار، تحقق من labels والشبكة والمنفذ قبل إيقاف حاوية `maskan-recovery-audit-rest` يدويًا؛ لا توقف حاوية مجهولة اعتمادًا على الاسم وحده.

لإيقاف Staging مع إبقاء الوحدات والنسخ:

```powershell
python supabase/staging/staging.py stop
```

## ب. التأكد من النسخ المتاحة — قراءة فقط

1. افتح مشروع `skngodvomygvxemfaefn` الصحيح في لوحة Supabase، ثم Database > Backups > Scheduled وPoint in Time.
2. دوّن الخطة، وجود النسخ، أقدم وأحدث توقيت، حالة كل نسخة ومدى PITR إن ظهر. لا تضغط Restore أو Enable أو Upgrade أو Download.
3. البديل: `python supabase/audit/backup_metadata.py` إذا توفر اعتماد إدارة معتمد في بيئة العملية. عنوان GET ثابت؛ لا تسجل الاعتماد أو تضعه في shell history أو Git. غيابه يعطي unverified.
4. لا تستخدم status=HEALTHY أو نجاح SELECT كبديل عن دليل النسخ. لقطة الشاشة المنقحة أو ملخص metadata يكفي لهذه المرحلة دون بيانات مستخدمين.

## ج. طلب الموافقة على نسخة حقيقية — لم يُنفذ

المقترح الأقل تعرضًا: نسخة منطقية PostgreSQL عبر TLS باتصال موثق إلى المشروع الصحيح، تُشفّر أثناء التدفق قبل الكتابة إلى قرص خارج المستودع، ثم استعادة في بيئة quarantine مستقلة. إذا توفر managed backup، راجع إمكان استعادة نسخة معزولة وتكلفتها أولًا؛ لا تفترض إمكان تنزيل physical backup أو أن إنشاء مشروع مدفوع مسموح.

تتطلب الموافقة تحديد العناصر التالية صراحة:

- السماح بقراءة وتصدير بيانات الإنتاج الحقيقية، ونطاق المخططات والملفات، والغرض واسم المسؤول والمراجعين.
- مجلد وجهة **خارج Git والمجلدات المتزامنة سحابيًا**، مثل قرص مشفر مخصص يحدده المستخدم؛ هذا المسار لم يُنشأ ولم يُعتمد بعد.
- تشفير موثق مثل age بمفتاح مستلم مستقل، مع حفظ المفتاح الخاص في مخزن منفصل وتحديد من يملك حق فك التشفير؛ تشفير القرص وحده لا يحمي نسخة منقولة.
- ACL محلي لحساب المسؤول المحدد فقط، وعدم إرسال الملف إلى GitHub أو خدمات خارجية، ومدة احتفاظ وحذف معتمدة.
- نافذة تشغيل، حدود الوقت والحمل، مساحة كافية، ومنع تداخل عمليات النسخ.
- موافقة منفصلة على استعادة البيانات الحقيقية في quarantine، ثم موافقة أخرى لأي تحويل إنتاجي أو تغيير إعدادات/اعتمادات أو ترحيل.

المحتوى المتوقع: مخططات وبيانات public/private/auth/storage، مستخدمون وpassword hashes ورموز جلسات محتملة وسجلات مالية ومعرفات وصلاحيات ودوال. ملفات الصور الثنائية منفصلة. إعدادات Edge وSMTP وOAuth ومفاتيح JWT/Vault ليست تلقائيًا حزمة استعادة كاملة؛ تُجرد أسماؤها ومالكوها دون كشف قيمها. نسخ الأدوار لا يحتاج تصدير كلمات مرورها.

الحجم الحالي من الكتالوج نحو 13.78MiB. خطط مبدئيًا لما لا يقل عن خمسة أضعاف الحجم المقاس للملفات المؤقتة والمخرجات والتحقق، زائد حجم Storage الحقيقي، ودون افتراض نسبة ضغط. يُفضل تخصيص 1GiB مشفر على الأقل للنسخة الصغيرة الحالية مع هامش، ومساحة منفصلة لصور Docker ووحدات PostgreSQL قد تحتاج عدة GiB. هذا تقدير تخطيط لا قياس لحجم backup أو خدمة مدفوعة.

## د. خطوات تنفيذ النسخة بعد الموافقة فقط

1. تحقق من هوية المشروع والوجهة والموافقات ومدة الاحتفاظ. استخدم إصدار pg_dump متوافقًا مع PostgreSQL 17 واتصال direct/session pooler موثقًا وTLS verify-full. لا تمرر كلمة المرور في command line؛ استخدم آلية اعتماد محمية ومؤقتة.
2. اضبط اتصال التصدير للقراءة فقط، مع مهلة قفل وحدود تشغيل مناسبة. راجع شمول Auth وStorage وprivate والإضافات والصلاحيات؛ لا تفترض أن أمر CLI افتراضي يغطي كل مخطط. لا تنفذ migration أو VALIDATE أو تغيير إعداد إنتاجي لتسهيل النسخ.
3. استخدم subprocess ثنائيًا يصل stdout الخاص بـpg_dump إلى stdin أداة التشفير؛ افحص رمزي الخروج معًا، وألغِ الناتج الجزئي إذا فشل أي طرف وفق سياسة معتمدة. لا تستخدم pipe نصيًا قد يفسد البايتات على Windows PowerShell.
4. احفظ manifest منقحًا فيه الزمن ونسخة الأدوات والنطاق وحجم ciphertext وبصمته. لا تنشر hashes صفوف الإنتاج أو بياناتها في Git. استبعد كلمات مرور الأدوار، وجرد الصلاحيات اللازمة للاستعادة.
5. اختبر فك التشفير ومحتويات الأرشيف داخل quarantine المصرح بها. نجاح إنشاء الملف وحده ليس نجاح backup. قياس RPO يعتمد على لحظة snapshot وتغيرات ما بعدها؛ RTO يشمل التجهيز والاستعادة والفحوص والتطبيق والملفات، وليس pg_restore وحده.

المخاطر: حمل قراءة وI/O على الإنتاج، snapshot طويل، تأخر في الملفات، تصدير أسرار داخل Auth/private، أو تسربها من logs والملفات المؤقتة. عند فشل شرط الأمان توقف؛ لا تتجاوز التشفير أو تتحول إلى نسخة غير محمية.

## هـ. استعادة حقيقية معزولة بعد موافقة منفصلة

1. استخدم بيئة جديدة بلا اتصال صادر إلى خدمات الإنتاج وبلا DNS أو credentials إنتاجية؛ أوقف البريد وwebhooks والوظائف المجدولة. لا تحملها في Staging الاصطناعي المشترك الحالي.
2. استعد الأدوار والمخطط والبيانات والفهارس والصلاحيات بترتيب متوافق، مع إيقاف عند الخطأ. لا تحذف قاعدة مجهولة أو تستخدم production restore لتجربة الخطة.
3. افحص الامتدادات، PK/FK/CHECK والفهارس وRLS وSECURITY DEFINER وsearch_path وgrants وviews security_invoker وAuth/Storage. تحقق من الأعداد والمجاميع داخل البيئة المقيدة دون نشر صفوف.
4. قبل تشغيل API، أبطل إمكانية استخدام رموز الإنتاج في النسخة، واضبط مفاتيح وإعدادات اختبار مستقلة. أي تنقيح لنسخة البيانات أو تغيير جلساتها يحتاج نطاق موافقة واضحًا. لا تحذف مستخدمين من الإنتاج.
5. استكمل اختبار Auth وتسجيل الدخول وEdge وRealtime وStorage والأجهزة؛ اختبار SDK المحلي الحالي لا يغطيها. سجل الفشل والوقت الفعلي قبل أي قرار تحويل.
6. لا تُحوّل الإنتاج تلقائيًا. القرار يحتاج نافذة وتعاملًا مع الكتابات اللاحقة للنسخة، ومراجعة من المسؤول وموافقة صريحة مستقلة.

## و. استعادة Storage المتسقة

الحالة المرصودة الآن: bucket `member-avatars` عام وعدد objects صفر، لكن التطبيق يتيح الرفع. بعد موافقة تشمل الملفات، جرد أسماء الكائنات وأحجامها وإصداراتها أو hashes في manifest مشفر داخل النطاق المقيد، لا في Git. نسخ metadata وحدها لا تعيد الصور.

للقطة متسقة لاحقًا: إما نافذة توقف كتابة **معتمدة** تشمل DB وStorage، أو نسخة أولية ثم جولة تغييرات وتحقق من عدم تغير manifest بين حدود snapshot. لا تنفذ هذا التوقف تحت موافقة التدقيق الحالية. عند الاستعادة اختر آلية رسمية متوافقة مع الخدمة: استعادة الكائنات عبر Storage API ثم مطابقة metadata، أو آلية self-hosted معتمدة لتخزينها. لا تعدل storage.objects يدويًا لإيهام النظام بوجود ملفات غير موجودة. افحص missing/orphan/mismatched objects وحقوق bucket والروابط بعد الاستعادة. الملفات المحذوفة بعد backup تحتاج النسخة الثنائية القديمة؛ restore DB لا يعيدها.

## ز. Android وiPhone — اختبار يدوي لم يُنفذ

سجل طراز الجهاز وإصدار OS وcommit ووقت الاختبار. استخدم مجموعات وأسماء وكلمات مرور اصطناعية، ولا تستخدم التطبيق المنشور إذا كان مضبوطًا على الإنتاج.

**Android عبر USB:** ابدأ Staging وEdge المحلي وفق README، ثم `adb devices` وحدد الجهاز. نفذ `adb -s <serial> reverse tcp:56321 tcp:56321`. أنشئ ملف dart-define محليًا مستبعدًا من Git، بمفتاح anon الخاص بـStaging وعنوان `http://127.0.0.1:56321` فقط، ثم `flutter run -d <serial> --dart-define-from-file=.codex_tmp/staging-device.private.json`. الملف يحتاج المفتاحين `SUPABASE_URL` و`SUPABASE_ANON_KEY` كما في المصدر. تحقق من سياسة HTTP لنسخة debug دون تخفيف إصدار الإنتاج. في النهاية أزل reverse باستخدام serial نفسه.

**iPhone Safari:** المسار الخاص للوصول من الجهاز إلى API والواجهة المحلية لم يُجهّز. قبل بدء الاختبار يلزم تصميم بوابة HTTPS خاصة أو نفق مقيد معتمد وتحديد اسم المضيف والشهادة وقائمة الأجهزة. لا تفتح Docker على 0.0.0.0 ولا تجعل داشبورد الاختبار عامًا ولا تغير إعدادات الإنتاج. اختبارات recovery GET تقبل loopback فقط ولا تُستخدم لتجاوز ذلك. بعد اعتماد المسار اضبط نسخة الويب المحلية على عنوان Staging الخاص المعتمد وافتحه في Safari؛ تأكد من المضيف في شريط العنوان ومن أن الحساب اصطناعي. إلى أن يتوفر ذلك تبقى خانة iPhone «غير منفذة».

على الجهازين بعد تجهيز الوصول:

1. أنشئ مجموعة A من Android وادخلها من Safari بحساب B. طابق العملة والأعضاء. أنشئ مجموعة ثانية مستقلة وتأكد من عدم ظهور بيانات الأولى.
2. أضف مصروفًا 10.00 بملاحظة اصطناعية؛ انتظر Realtime على الآخر وطابق الإجمالي. عدّل إلى 11.00 من الكاتب، وتحقق من رفض تعديل عضو آخر.
3. اقطع الشبكة قبل الإرسال، ثم أعدها واضغط إعادة المحاولة. كرر مع قطعها بعد الحفظ المحتمل. المتوقع مصروف واحد لا اثنان. عند تعارض محتوى حقيقي تبقى رسالة واضحة، ولا يظهر نجاح وهمي.
4. اطلب reset من العضو غير المالك؛ تأكد من عدم الإغلاق قبل الموافقات. وافق من الآخر وأعد الضغط؛ المتوقع إغلاق واحد ودورة تالية واحدة وأرشفة سليمة.
5. حاول تعديل وحذف المصروف المؤرشف؛ يجب أن يبقى دون تغيير. حاول إغلاق الدورة وإرسال مصروف من الجهاز الآخر بالتزامن؛ لا يُنقل مصروف صامتًا إلى دورة أخرى.
6. أغلق الشاشة أو ضع التطبيق بالخلفية ثم أعد الاتصال؛ تحقق من تحديث Realtime وعدم تكرار المصاريف أو الإشعارات. اختبر انتهاء الجلسة ثم تسجيل الدخول مجددًا بحساب الاختبار.
7. افحص RTL والتكبير ولوحة المفاتيح والنافذة ورسائل الخطأ وعدم التمرير الأفقي. سجل كل نتيجة مع دليل منقح. لا تعتبر أي بند ناجحًا لمجرد نجاح Chromium/WebKit.

## ح. بوابة القرار

أي فقد بيانات أو كسر RLS أو عدم تحقق backup ينتج NO-GO. لا تُطبق migration الأمن ولا تُنشر الواجهات قبل اعتماد خطة النسخة والتحقق من الاستعادة والأجهزة. إذا فشل الترحيل مستقبلًا داخل المعاملة، تحقق من rollback؛ إذا نجح ثم ظهرت مشكلة مع كتابات جديدة، فضّل إصلاحًا أماميًا مدروسًا أو استعادة معزولة مع تسوية الكتابات، ولا تحذف الأرشيف أو تعيد قاعدة قديمة فوق إنتاج نشط تلقائيًا.

تنبيه توثيقي للأجهزة القديمة: [إعلان Supabase بتاريخ 12 أكتوبر 2026](https://supabase.com/changelog/cbc-tls-ciphers-deprecated) يحدد إزالة بعض TLS 1.2 CBC ابتداءً من 10 نوفمبر 2026 على الأقل. الاختبار المحلي HTTP لا يثبت توافق TLS المستضاف؛ أضفه إلى بوابة الأجهزة قبل النشر.
