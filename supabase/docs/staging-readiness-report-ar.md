# تقرير Maskan للتحقق من Staging والجاهزية للإنتاج

التاريخ: 2026-10-18. الفرع: `validation/maskan-staging-readiness`.
الأساس الأمني: `df1fbfb4f9c3ad5bccdbeb0c6555bb57061588c4`.

## 1. الهدف والقرار

استكمال التحقق من الترحيل الأمني في بيئة مستقلة دون إعادة بناء المشروع أو إعادة الاختبارات الناجحة بلا سبب. **التوصية: NO-GO للإنتاج حاليًا**. نجاح الاختبارات المحلية يسمح بمواصلة التحقق المعزول، لكنه لا يحل محل اختبارات الأجهزة الفعلية ومراجعة اختلافات قاعدة الإنتاج وخطة استعادتها. لم يُنفذ أي تعديل أو ترحيل أو نشر على Supabase الإنتاجي، ولم يُنشر التطبيق أو الداشبورد ولم يُدمج main.

## 2. المعمارية والعزل

بيئة `maskan-staging-validation` مستقلة عن الإنتاج وعن `maskan-hardening-local` السابق؛ بياناتها مولدة اصطناعيًا. Supabase CLI مثبت على 2.115.0. الحاويات والشبكة ووحدات التخزين وكلمات المرور وJWT خاصة بهذه البيئة. واجهة API على `127.0.0.1:56321`، PostgreSQL على `127.0.0.1:56322` والبريد المحلي على `127.0.0.1:56324`. الاستعادة تمت في `maskan-staging-recovery` بشبكة ووحدة تخزين وكلمة مرور مستقلة ومنفذ `127.0.0.1:57322`.

فشل اتصال المضيف مع شبكة Docker ذات `internal` في هذا الجهاز. الحل شبكة bridge مخصصة مع ربط المنافذ المنشورة بالـ loopback فقط، وليس فتحها للعامة. تحقق فعلي أثبت ملكية الحاويات، اختلاف وحدات التخزين عن البيئة السابقة، رفض كلمة المرور الخاطئة، قبول المفتاح الصحيح ورفض الخاطئ بـ401، واتجاه Edge إلى gateway المحلي. هذا **ليس جدارًا ناريًا يمنع كل خروج من الحاويات**؛ أدوات الاختبار تضيف رفضًا صريحًا لأي وجهة HTTP خارج الأصل المحلي المسموح ولإعادة التوجيه. لا ندعي تكافؤ هذه البنية مع العزل الشبكي الكامل أو بنية Supabase المستضافة.

قبل العمليات المدمرة تتحقق الأدوات من هوية المشروع والمجلد والحاوية والشبكة ووحدة التخزين والمنفذ. تُرفض المشاريع المرتبطة والسحابة وDocker البعيد ومعرف الإنتاج. لا يوجد تمرير عام لأوامر CLI أو URL إنتاجي. كلمات المرور والملفات الخاصة والنسخ والسجلات داخل `.codex_tmp` المستبعد من Git. لا توجد بيانات مستخدمين حقيقية في fixtures.

## 4. الترحيل وسلامة البيانات — ناجح

نجحت سلسلة migrations على قاعدة نظيفة؛ استغرق الترحيل الأمني 0.450 ثانية. ونجحت الترقية من البنية السابقة مع 4,000 مصروف اصطناعي مجموعها 8,402,000 سنت، وطلب موافقة معلق؛ استغرقت 0.626 ثانية، دون فهارس غير صالحة أو إغلاق تلقائي للطلب القديم.

رُفضت بأمان ثلاث حالات تاريخية غير سليمة: دورتان مفتوحتان، مصروف غير مؤرشف على دورة مغلقة، ولقطة ناخبين غير آمنة. إنهاء اتصال الترحيل بعد DDL أعاد المعاملة وحافظ على المال. التعارض مع قفل جدول أنهى الترحيل عبر مهلة القفل خلال 5.654 ثانية دون ترحيل جزئي.

نجح سابقًا في هذه البيئة نفسها 57 فحصًا حقيقيًا لـSQL/RLS والتزامن: حماية المصاريف المؤرشفة، عزل المجموعات، هوية الكاتب، الإغلاق مرة واحدة، الطلبات والموافقات، مسارات Android القديمة، الصلاحيات وSECURITY DEFINER. لم تُكرر هذه المجموعة الناجحة بعد تغييرات أدوات HTTP التي لا تمس منطق SQL.

## 5. الحمل والتزامن والفشل — ناجح مع أخطاء مؤقتة متوقعة

أربعة عمال، 16 عملية منطقية و32 إرسالًا نتج عنها 48 محاولة HTTP. حدث 16 تعارضًا مؤقتًا و4 حالات نفاد للمحاولات الأولية المحدودة. نجحت إعادة المحاولة الصريحة اللاحقة بنفس المعرف؛ النتيجة 16 مصروفًا وصفر تكرار. لا يُفهم ذلك على أن جميع الطلبات نجحت من المحاولة الأولى.

زمن الطلب: p50=19.97ms، p95=83.50ms، الأقصى=98.33ms؛ إجمالي السيناريو 3.799 ثانية. ثمانية طلبات إغلاق متزامنة أحدثت إغلاقًا واحدًا فقط. إنهاء جلسة أثناء إدخال مصروف ألغى الإدخال. اختبار مستقل رصد قفل advisory ينتظره طلب فعلي 4022.93ms؛ أعاد الطلب الثاني false بعد الإغلاق الأول، دون deadlock. هذه قياسات حمل محلي محدود، وليست تقديرًا لسعة آلاف المستخدمين في الإنتاج.

## 6. النسخ والاستعادة — ناجح ضمن النطاق

حجم النسخة 620702 بايت، SHA256: `5b64d0fdba8ef1f45ec4ceee8c07cd9f0be15380cc871da0e71245b56f80f89d`.
النسخ 0.593 ثانية والاستعادة 2.86 ثانية. تمت مقارنة 46 جدولًا في public/private/auth/storage: تطابقت بصمات الصفوف، الأعمدة، الفهارس، RLS، تعريفات ومالكو الدوال والصلاحيات. مقارنة ACL توسع الصلاحيات الافتراضية بدل إسقاطها. لقطة التحقق: 4022 مصروفًا، 8,451,700 سنت، 20 مؤرشفًا و20 دورة.

هذه مقارنة عند لحظة النسخ؛ أضيفت fixtures لاحقة إلى Staging فلا يُدعى تطابق القاعدتين حاليًا. ملفات Storage الثنائية ليست ضمن pg_dump ولم يُختبر استرجاع صورة مستخدم. كذلك لم يُختبر PITR أو backup فعلي للإنتاج. نجح stop/start مع بقاء لقطة 4028 مصروفًا ومجموع 8,464,003 سنت وصحة API.

## 8. المحاولات الفاشلة والمتخطاة

المحاولات الأولية الفاشلة محفوظة في سجل النتائج وليست مخفية: اتصال internal، تهيئة صلاحيات أدوار قاعدة محلية، عنوان Edge الداخلي، اسم tenant في Realtime، أدوار الاستعادة ومقارنة تمثيل ACL، طباعة UTF-8 على Windows، وتحليل Flutter بسبب http غير المعلن مباشرة. عولجت أسبابها وأعيد التحقق المتأثر. أخطاء الحمل المؤقتة المذكورة أعلاه جزء من اختبار إدارة التعارض وليست فقد بيانات.

اختبارات الأجهزة الفعلية Android/iPhone لم تُنفذ؛ WebKit محاكاة متصفح وليست جهاز iPhone. سيناريوهات التكامل المشروطة تتخطى عمدًا في مجموعة Flutter العامة وتُشغّل منفصلة وقد نجحت. لم تُختبر استعادة ملفات Storage الثنائية أو PITR الإنتاج أو تكافؤ إعدادات الإنتاج أو حمل واسع. لا يُصنف أي منها ناجحًا.

## 10. التشغيل المحلي والتحقق اليدوي

من جذر المستودع، بعد تثبيت Docker وPython وNode وFlutter والاعتمادات:

```powershell
python supabase/staging/staging.py start
python supabase/staging/staging.py inspect
python supabase/staging/staging.py serve
```

يعمل serve في نافذة مستقلة. لا تُشغّل reset أو rehearse أثناء اختبارات أخرى؛ فهي تمس Staging الاصطناعي فقط. أوامر إعادة التحقق عند الحاجة:

```powershell
python -m unittest discover -s supabase/staging -p test_safety.py -v
python supabase/staging/isolation_check.py

python supabase/staging/run_suite.py sql

python supabase/staging/run_suite.py flutter
python supabase/staging/run_suite.py web
python supabase/staging/run_suite.py edge
python supabase/staging/run_suite.py browser

```

راجع [دليل الأدوات](../staging/README.md) و[خطة الأجهزة الفعلية](staging-device-test-plan-ar.md). قائمة التحقق اليدوية: حسابان اصطناعيان في مجموعة وحساب في أخرى؛ التأكد من العزل، إضافة مصروف وإعادة المحاولة بعد انقطاع، تعارض محتوى حقيقي ورسالة مفهومة، إغلاق متزامن، طلب موافقة، أرشفة غير قابلة للتعديل، خروج عضو، وإعادة تسجيل الدخول. تبقى هذه القائمة على الأجهزة الفعلية معلقة حتى تسجيل الجهاز والإصدار والنتيجة.

## 11. خطة التطبيق المستقبلية والتراجع

بعد موافقة صريحة مستقلة: جرد إعدادات ومخطط الإنتاج للقراءة فقط ومقارنتها بالأساس المختبر؛ معالجة البيانات التاريخية غير الصالحة بخطة معتمدة؛ أخذ نسخة إنتاج والتحقق من استعادتها وStorage/PITR؛ استكمال الأجهزة؛ اختيار نافذة هادئة وتطبيق migration المعاملاتي ثم فحوص قراءة للصلاحيات والمجاميع والدورات. أي نشر Edge أو تطبيق يحتاج خطة وموافقة منفصلتين. تُراقب أخطاء 40001 ومعدلات retry وزمن الانتظار.

إذا فشل الترحيل داخل المعاملة فالتراجع تلقائي. بعد نجاحه ووجود كتابات جديدة، يُفضّل إصلاح أمامي آمن؛ لا إسقاط عشوائي للسياسات ولا إزالة الأرشفة أو حذف التاريخ المالي. الاسترجاع من النسخة يبدأ في قاعدة منفصلة مع مطابقة البيانات وتسوية الكتابات اللاحقة ثم قرار تحويل معتمد. إيقاف Staging لا يحذف وحدات التخزين.
