# تقرير Maskan Backend Security Hardening

تاريخ التحقق: 18 أكتوبر 2026. الفرع: `security/maskan-backend-hardening`، مبني على `7fab19e68377822f34911e647ae33a2a66ac55b5` من فرع الداشبورد. التنفيذ استكمل التعديلات المحلية السابقة ولم يبدأ مشروعًا جديدًا.

## 1. الهدف والنطاق

حماية سلامة المصاريف والدورات والموافقات على الخادم، وإصلاح إعادة الإرسال المتزامنة، مع الحفاظ على واجهات Flutter Android والويب. التسليم يشمل المصادر والترحيل والاختبارات والتوثيق فقط. لم تُغيَّر قاعدة الإنتاج أو RLS الحية أو Edge المنشورة، ولم يُنشر الداشبورد أو يُدمج الفرع مع main أو تُستخدم خدمة مدفوعة.

## 2. التعديلات والأثر المعماري

- **المصاريف المؤرشفة:** سياسات RLS وحارس قاعدة بيانات يمنعان تعديلها أو حذفها من العميل، ويحميان الكاتب والدافع والدورة ومعرّف العملية. تبقى عمليات إخفاء الهوية الموثوقة عند حذف الحساب ممكنة، دون تغيير المبالغ التاريخية.
- **إعادة الإرسال:** المعرّف نفسه يعاد استخدامه عند تكرار النموذج دون تغيير. التحقق من التطابق يشمل المجموعة والدورة والكاتب والدافع والمبلغ والملاحظة والمعرّف. اختلاف البيانات يسبب `expense_operation_conflict`، بينما المعرّفات المختلفة تسمح بمصاريف مستقلة حتى لو تطابق المحتوى.
- **التزامن:** قفل معاملات لكل مجموعة، وفهرس يضمن دورة مفتوحة واحدة. الحراس المباشرة تستخدم try-lock لتجنب عكس ترتيب أقفال الصفوف؛ يرجع التعارض المؤقت `40001/network_busy_retry`. يعيد العميل المحاولة مرتين فقط بالبيانات والدورة والمعرّف الأصليين. لا يعيد تلقائيًا طلبًا ذا دورة قديمة أو فشل نقل غامض.
- **إغلاق الدورة:** الأرشفة والإغلاق وإنشاء الدورة التالية وإكمال الطلب والإشعارات عملية واحدة. إعادة الإغلاق لا تكرر الأثر، ولا يمكن للمالك تجاوز موافقات طلب معلّق.
- **الموافقات:** قائمة المصوّتين تُشتق من العضوية على الخادم، والموافقة الأولية وعلامة الانتظار والإشعارات ذرية. آخر موافقة تكمل العملية دون اعتماد على استمرار اتصال العميل. تُدعم إعادة إرسال INSERT وmerge-upsert من Android الحالي.
- **العضوية:** إعادة التحقق بعد انتظار القفل، وإلغاء الطلب المتأثر بخروج عضو، وحماية الإلغاء والحذف وفق الحالة والصلاحية.
- **الصلاحيات:** مراجعة 59 توقيع دالة؛ تثبيت search_path، وإلغاء التنفيذ المكشوف لتسعة مساعدات قديمة، وعدم إتاحة أي SECURITY DEFINER تطبيقي لـanon. التفاصيل في [جرد الدوال](backend-function-inventory.md).
- **المصادقة والحذف:** تحديد المعدل لا يعتمد على ترويسات IP القابلة للتزوير. سلطة الحذف من العضوية الدائمة والتحقق من كلمة المرور والقدرة ذات الاستخدام الواحد، وليس user_metadata. إبطال جلسات التحديث قبل حذف مستخدم Auth. تنقيح السجلات لمنع تسريب أجزاء طلبات JSON التالفة.
- **الأداء:** عشرة فهارس للمفاتيح الخارجية، دون حذف فهارس أو إعادة كتابة النظام. لا تغيير لعقد AuthV2 أو دقة المبالغ أو الجداول الأساسية.
- **الرسائل:** رسائل عربية واضحة في نافذة المصروف على الويب، ورسائل عربية وإنجليزية في Android. التعديلات لا تغيّر الهوية البصرية.

## 5. التوافق والحدود والمخاطر المتبقية

- مسارات Android المنشور مدعومة ومختبرة على مستوى SQL وREST: إدخال الطلب والموافقة، تحديث علامة الدورة، merge-upsert، والإكمال boolean. تحسين تجربة إعادة المحاولة في التطبيق نفسه يحتاج إصدار Android منفصل لاحقًا. لم يُنشأ أو يُنشر إصدار متجر في هذه المهمة.
- الويب يستخدم RPC الجديدة مع رجوع للمسار القديم فقط عند `PGRST202`؛ أخطاء الصلاحية أو الشبكة لا تسبب كتابة بديلة.
- لا تمثل الاختبارات المحلية ضمانًا للأجهزة الفعلية أو لحمل الإنتاج. يلزم فحص Android فعلي وiPhone قبل إطلاق أي إصدار.
- توجد **5 نتائج عالية في أدوات التطوير** بسلسلة braces/Next lint بحسب التدقيق الكامل. لا نتائج runtime. لم يُستخدم audit fix --force لأنه يقترح تغيير إصدار رئيسي غير متوافق؛ تحتاج تبعيات التطوير معالجة منفصلة ومدروسة.
- إنشاء الفهارس داخل معاملة بحد انتظار قفل 5 ثوانٍ وحد تنفيذ 60 ثانية قد يفشل بأمان على إنتاج كبير أو مزدحم. يلزم قياس وتجربة staging قبل الاعتماد.
- الحصص المربوطة بالحساب تمنع تجاوزها بتغيير IP، لكنها قد تسمح بإزعاج حساب مستهدف بمحاولات كثيرة؛ يلزم رصد وضبط البوابة الموثوقة.
- JWT الصادر سابقًا قد يبقى صالح التوقيع حتى انتهاء مدته؛ حذف العضوية يمنع الوصول لبيانات التطبيق فورًا. فشل جزئي بين Storage وAuth وقاعدة البيانات يحتاج تجربة استعادة على staging. إعدادات كلمات المرور والتسجيل والحماية من كلمات المرور المسرّبة لم تُغيّر حيًا.
- الترحيل يرفض التاريخ غير المتسق بدل إصلاحه بالتخمين. لا تعتبر أي إصلاحات هنا مطبّقة على الإنتاج.

## 6. التشغيل المحلي وقائمة التحقق اليدوية

من جذر المشروع، مع Docker وNode وFlutter وPython:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File supabase/tests/run_backend_hardening.ps1 -ResetDisposableDatabase
npx --yes supabase functions serve --workdir .codex_tmp/maskan-hardening-local
```

الخيار Reset يحذف فقط بيانات المشروع المحلي المخصص. لا تستعمل مشروعًا مشتركًا أو عنوان إنتاج. في نافذة أخرى التقط `supabase status --output json` داخل متغيرات، دون طباعة المفاتيح، واضبط متغيرات الاختبار المحلية كما في [دليل التنفيذ](backend-hardening.md). ثم:

```powershell
flutter analyze --no-pub
flutter test --no-pub
node --import ./web-dashboard/node_modules/tsx/dist/loader.mjs --test supabase/tests/edge_hardening.test.mts
npx --yes deno check supabase/functions/maskan-password/index.ts supabase/functions/maskan-delete-account/index.ts
cd web-dashboard
npm ci
npm run typecheck
npm run lint
npm test
npm run test:integration
npm run build
npm run test:browser -- --workers=1
npm run dev
```

للتشغيل التفاعلي استخدم إعدادات Supabase المحلي في `web-dashboard/.env.local` وفق `.env.example`، وبالمفتاح العام المحلي فقط. الصفحة على `http://127.0.0.1:3000`. لا تُضمّن الملف في Git. شغّل اختبارات المتصفح بعد انتهاء الاختبارات الثقيلة. تشغيل Flutter التفاعلي يستخدم متغيرات `SUPABASE_URL` و`SUPABASE_ANON_KEY` عبر dart-define بإعدادات محلية.

قائمة تحقق يدوية قبل إطلاق لاحق:

- أنشئ مجموعتين اصطناعيتين وأعضاء مختلفين؛ تحقق من عزل السجل والأحداث.
- أعد حفظ المصروف نفسه بعد انقطاع، ثم غيّر مبلغًا أو دافعًا؛ تحقق من العدد والرسالة داخل النافذة.
- أغلق الدورة من عميلين مع إرسال مصروف؛ تحقق من دورة تالية واحدة وعدم ترحيل مصروف قديم بصمت.
- نفّذ طلبًا من عضو عادي، وأعد الموافقة من Android والويب؛ تحقق من عدم تكرار الإشعارات ومن منع تجاوز الأصوات.
- حاول تعديل وحذف المصروف المؤرشف، ثم تحقق من بقاء المبلغ والسجل.
- تحقق على هاتف فعلي وسطح مكتب من RTL والنافذة والرسائل والتمرير والألوان.

## 7. التطبيق المستقبلي والتراجع

قبل أي تطبيق إنتاجي: مراجعة التعريفات والصلاحيات الحية للقراءة فقط، ونسخة احتياطية/PITR مختبرة، وتجربة staging تشمل البيانات التاريخية والحمل ومسارات Android المنشور، ثم **موافقة صريحة**. الترحيل هو ملف واحد داخل معاملة؛ فشل preflight أو القفل يلغي المعاملة. نشر Edge أو الويب أو Android يحتاج موافقة منفصلة.

بعد اعتماد لاحق، راقب عدد الدورات المفتوحة، وسلامة الأرشيف، وأعمار الطلبات، والتعارضات، وزمن الإغلاق، وأخطاء الحذف، دون تسجيل أسرار أو بيانات مستخدمين.

التراجع المفضل بعد commit قاعدة البيانات هو إصلاح أمامي مدروس مع إيقاف الكتابات المتأثرة عند الضرورة. لا تفك الأرشفة أو تعيد فتح دورات مغلقة أو تحذف تاريخًا. يمكن إعادة artifacts التطبيق السابقة مع إبقاء حراس السلامة. التراجع الشامل بعد كتابات جديدة يحتاج موافقة وإيقاف كتابة واستعادة نسخة إلى هدف معزول ومصالحة البيانات قبل التحويل. التفاصيل في [خطة التطبيق والتراجع](backend-hardening.md).
