# تدقيق نسخ الإنتاج والتعافي من الكوارث — Maskan

تاريخ الفحص: 2026-10-18. الأساس: `1337c9ece0f6bd0be1439e4292ce7c6d6ae74795`.
الفرع: `validation/maskan-production-recovery-audit`. المشروع المستهدف للقراءة فقط: `skngodvomygvxemfaefn`.

## الهدف والقرار

التحقق من جاهزية النسخ والاستعادة دون تعديل الإنتاج أو نسخ بيانات مستخدمين حقيقية. **NO-GO لتطبيق الترحيل أو الادعاء بجاهزية التعافي الإنتاجي**؛ وجود نسخة إنتاج قابلة للاستعادة لم يثبت. نجحت بروفة الاستعادة الاصطناعية وإعادة اتصال مكتبات الواجهتين، وهي دليل محلي محدود وليست إثباتًا لاستعادة الإنتاج.

لم تُنفذ migrations أو تغييرات RLS أو نشر Edge أو تغيير Auth/Storage أو كلمات المرور على الإنتاج. لم تُنزل نسخة إنتاج أو صور أو معاملات أو رموز أو بيانات مستخدمين. القراءة اقتصرت على خصائص المشروع والخطة وكتالوج المخطط وعدادات إجمالية. لم تُفعّل خدمات مدفوعة ولم يُدمج main.

## نسخة الإنتاج والخطة

| البند | النتيجة والدليل |
|---|---|
| الخطة | Free مؤكدة عبر Supabase get_organization |
| حالة المشروع | ACTIVE_HEALTHY؛ ليست دليلًا على وجود backup |
| PostgreSQL | إصدار الخدمة 17.6.1.121، وserver_version من SQL يساوي 17.6 |
| الحجم | 14,445,715 بايت تقريبًا 13.78MiB؛ قياس لحظي لا يمثل حجم dump مضمونًا |
| الإضافات المثبتة | pg_stat_statements 1.11، pgcrypto 1.3، plpgsql 1.0، supabase_vault 0.3.1، uuid-ossp 1.1 |
| جرد النسخ المدارة | غير متحقق: الموصل المتاح لا يوفر listing للنسخ، ولا يوجد SUPABASE_ACCESS_TOKEN في بيئة العملية |
| PITR الحالي | لم تُفحص إعداداته الحية؛ ليس ميزة مشمولة في Free وفق التوثيق |
| تاريخ آخر نسخة/مدة الاحتفاظ الفعلية | غير معروفين، ولا توجد نسخة تم فحص استعادتها |

وفق [وثائق Supabase للنسخ](https://supabase.com/docs/guides/platform/backups)، النسخ اليومية المتاحة مرتبطة بخطط Pro/Team/Enterprise واحتفاظها المعتاد 7/14/30 يومًا؛ Free تحتاج استراتيجية تصدير مستقلة. PITR إضافة مدفوعة للخطط المؤهلة، وليست تفعيلًا مصرحًا به هنا. لا نستنتج وجود نسخة قابلة للاستخدام من إصدار PostgreSQL أو حالة HEALTHY. ملف `backup_metadata.py` يتيح GET ثابتًا لبيانات النسخ الوصفية فقط عند توفير اعتماد إدارة معتمد؛ لا ينزل النسخ ولا يتبع redirects. شُغّل دون اعتماد وسجل unverified دون اتصال.

نسخة قاعدة كاملة تشمل بنية وبيانات Auth وبيانات Storage الوصفية ضمن نطاقها؛ أوامر التصدير التي تستبعد مخططات النظام لا تُعد بديلًا كاملًا تلقائيًا. ملفات Storage الثنائية لا تدخل في نسخة قاعدة البيانات. دليلنا المحلي قارن auth/storage فعليًا، لكن لا نملك ملف إنتاج لنتحقق من نطاقه. [مرجع النقل والاستعادة الرسمي](https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore).

## المخطط وسلامة البيانات — قراءة فقط

حُفظت ثلاث استعلامات SELECT منفردة وقابلة للمراجعة تحت `supabase/audit`، دون SQL تنفيذي مدمر أو استدعاءات RPC تطبيقية. الجرد يغطي 477 تعريف عمود، 192 قيدًا في مخططات التطبيق/Auth/Storage، الفهارس، RLS، صلاحيات الأعمدة والدوال، SECURITY DEFINER، triggers، وخمس migrations حتى `20260826000000`. لا توجد migration الأمن `20261017194224` في تاريخ الإنتاج.

النتائج الإجمالية الجديدة: صفر دورات مفتوحة مكررة، صفر إسنادات مصروف نشط غير سليمة، صفر لقطات موافقة معلقة غير آمنة، وصفر دورات مصروف مفقودة أو لقطات معلقة null. عدد طلبات reset والموافقات حاليًا صفر، ولذلك لا يوجد تاريخ غير فارغ لمراجعته. الاختبارات الاصطناعية السابقة تغطي هذه الحالات، ولا تُنسب نتائجها للإنتاج.

القيود التسعة NOT VALID باقية: ستة CHECK وثلاثة FK. فحص المخالفات الحالية المقابلة لها أعاد صفرًا: حالات الدورة والطلب والإشعار، المبلغ غير الموجب، طول الملاحظات، ومراجع الكاتب والدافع وصاحب الطلب. لم ننفذ VALIDATE CONSTRAINT؛ عدم وجود مخالفات الآن لا يحول هذه القيود إلى validated ولا يضمن عدم تغير البيانات لاحقًا.

جداول التطبيق الأساسية لديها RLS. العرضان `maskan_networks` و`maskan_network_members` يحملان `security_invoker=true`؛ قيم RLS=false لهما ليست جداول تطبيق بلا حماية. توجد ثلاثة triggers تطبيقية في الإنتاج.

## الفروق عن النسخة المقوّاة

- 46 توقيع دالة في الإنتاج مقابل 59 في Staging المقوّى؛ 13 دالة جديدة، تشمل حراس المعاملات والموافقات وRPC الجديدة.
- 11 فهرسًا إضافيًا في Staging، منها فهرس دورة مفتوحة واحدة وعشرة فهارس FK.
- سياسات UPDATE/DELETE للمصروف في الإنتاج تتحقق من الكاتب، لكنها لا تحتوي شرط `archived_at is null` الجديد. لم تُجرب كتابة إنتاجية لإثبات استغلال.
- توجد 10 دوال SECURITY DEFINER متاحة لـanon في الإنتاج، بينها إكمال الدورة وتسعة مساعدات phase5؛ مقابل صفر في Staging. الإتاحة ليست وحدها إثبات تجاوز داخل جسم كل دالة، لكنها فرق صلاحيات مهم يعالجه الترحيل.
- اختلفت بصمات النص الكامل لـ34 تعريف دالة مشتركة. البصمة تتأثر بـsearch_path وتنسيق التعريف أيضًا؛ لا تعني 34 اختلافًا وظيفيًا مستقلًا. لا تُعتبر هذه المقارنة موافقة تلقائية على استبدال دوال الإنتاج.
- سجل migrations المحلي غير موجود لأن البروفة تنفذ ملفات SQL مباشرة؛ قورنت قائمة الإنتاج بالملفات والنتائج السابقة بدل اختلاق سجل محلي.

لا توجد حاليًا عوائق البيانات الثلاثة التي يفحصها الترحيل. تبقى جاهزية النسخ والاستعادة، مراجعة الفروق الدلالية، القيود غير المعتمدة، نافذة الأقفال والأجهزة بوابات اعتماد مستقلة. لم تُعدل أي migration.

## Storage والخصوصية

`lib/services/member_avatar_photo_service.dart` يستخدم uploadBinary وgetPublicUrl في bucket `member-avatars`، مع صلاحيات معرفة في migrations. لذلك Storage مستخدم في التصميم وليس ميزة غير مستخدمة. القراءة الحية وجدت bucket عامًا واحدًا وصفر كائنات وصفر بايت مبلغ عنه حاليًا. لم تُقرأ أسماء كائنات أو صور أو أسماء مستخدمين. خلوه الآن لا يثبت عدم وجود رفع مستقبلًا أو ملفات يتيمة في طبقة الخدمة.

خطة الاستعادة يجب أن تجمع snapshot قاعدة البيانات مع manifest للكائنات ونسخها الثنائية عند وجودها، ومعالجة التغيرات بين اللقطتين. لا يعيد restore قاعدة قديمة صورة حُذفت لاحقًا. أي تنزيل حقيقي، بما فيه صور bucket عام، يحتاج موافقة مستقلة في هذه المهمة. راجع دليل التشغيل المرفق.

نسخة حقيقية قد تحتوي بيانات مالية وأسماء ومعرفات وpassword hashes وجلسات Auth ورموز refresh وبيانات private/Vault؛ لا تعاملها كملف SQL عادي. يلزم تشفير قبل الكتابة، مفاتيح منفصلة، قائمة وصول محددة، مدة احتفاظ وحذف معتمدة، ودليل استعادة معزول دون رسائل بريد أو webhooks أو اتصال بالإنتاج. لم تُختبر إمكانية فك أسرار Vault المنقولة؛ تعتمد على مفاتيح وإعدادات منفصلة يجب جردها دون كشفها.

## المخاطر والقرار التالي

| الشدة | الخطر/البوابة |
|---|---|
| عالية | وجود backup إنتاج قابل للاستعادة وتاريخه غير مثبتين؛ RPO/RTO الإنتاج غير مقاسين |
| عالية | الترحيل الأمني غير مطبق والفروق في الأرشفة والصلاحيات ما زالت حية |
| عالية | استعادة Auth والملفات والإعدادات والمفاتيح في خدمة كاملة لم تُثبت |
| متوسطة | تسعة قيود NOT VALID، رغم صفر مخالفات مرصودة الآن |
| متوسطة | مقارنة بصمات الدوال لا تغني عن مراجعة الفروق الدلالية قبل الاعتماد |
| متوسطة | اختبار SDK لا يساوي اختبار Android/iPhone فعلي أو إعادة تسجيل الدخول |
| متوسطة | bridge المحلي ليس جدار منع خروج؛ الحواجز تمنع التوجيه العرضي إلى الإنتاج |

القرار **NO-GO للإنتاج**. الخطوة التالية: التحقق من صفحة Backups/PITR للقراءة فقط وتسجيل وجود نسخة وتواريخها، ثم موافقة منفصلة على خطة نسخة حقيقية مشفرة واستعادتها في quarantine. لا تحتاج هذه المهمة إلى تنزيل بيانات حقيقية كي تنتهي كتدقيق ذي حدود موثقة؛ توقفت قبل هذه الخطوة.
